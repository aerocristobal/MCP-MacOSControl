# OSCAL Artifacts

This directory holds the machine-readable compliance posture for MCP-MacOSControl.
The artifacts are consumed by downstream SSP-assembly tooling and by the
project's own drift-detection tests; both treat them as authoritative for
NIST SP 800-53 control coverage, accepted-risk decisions, and continuous-
monitoring evidence.

## Files

| Path | Purpose |
|---|---|
| `component-definition.json` | OSCAL 1.1.2 Component Definition. One component (the MCP server), one control-implementation block targeting the NIST SP 800-53 r5 catalog, and one `implemented-requirement` per control documented in `docs/SECURITY.md` §7 and §8. Maintained per STORY-022. |
| `plan-of-action-and-milestones.json` | OSCAL 1.1.2 POA&M. One open item per `docs/SECURITY.md` §4 accepted-risk statement, plus historical closed items (e.g. the pre-STORY-024 deferred audit sink). Maintained per STORY-037. |
| `assessment-results.json` | OSCAL 1.1.2 Assessment Results. Continuous-monitoring observations generated by `swift run oscal-emit` from the STORY-024 `AuditRecord` JSONL stream. Append-only. Maintained per STORY-037. |
| `poam-id-allocations.md` | UUID registry for POA&M items so two PRs cannot race to use the same identifier. |
| `assessment-results-mapping.md` | Human-readable companion to `EventTypeMapping.swift`: AuditRecord event types → OSCAL Observation `title` + `methods` + control links. |
| `known-warnings.md` | `oscal-cli` warnings the maintainers have reviewed and accepted. Empty by default; additions require a security-labelled PR. |

## Maintenance workflow

The OSCAL artifact and `docs/SECURITY.md` are maintained **separately**. The
prose is authored for human reviewers; the OSCAL artifact is authored for
machine consumers. A CI drift check catches divergence in either direction:

- If `SECURITY.md` names a control (e.g. **NEW-X**) that `component-definition.json`
  does not implement → the `OscalCoverageCheckerTests` `missingControls` test
  fails with the offending control id.
- If `component-definition.json` implements a control that `SECURITY.md` does
  not reference → the `extraControls` test fails. (Recovery: either remove the
  OSCAL statement or add the prose mention.)

### When to update the OSCAL artifact

Update `component-definition.json` whenever any of the following lands:

1. A new control is mapped in `docs/SECURITY.md` §7.1 or §8.x.
2. A documented control changes implementation status (e.g. a `partial` becomes `implemented`).
3. A source file referenced by an `implementation` link is renamed or removed.
4. A new accepted residual risk is added to `SECURITY.md` §4 (record as a
   `statements[]` entry with `remarks` under the corresponding control,
   following the SI-10 pattern).

### Update mechanics

1. Edit `component-definition.json`.
2. Bump `metadata.last-modified` to the current UTC timestamp
   (`date -u +"%Y-%m-%dT%H:%M:%SZ"`).
3. Bump `metadata.version` if the change is consumer-visible (added/removed
   controls, changed `implementation-status`). Pure prose tweaks keep the
   version.
4. Generate fresh UUIDs for any new `implemented-requirement` or `statement`
   (`uuidgen | tr 'A-Z' 'a-z'`).
5. Validate locally:
   ```bash
   docker run --rm -v "${PWD}:/work" -w /work \
     ghcr.io/metaschema-framework/oscal-cli:latest \
     validate oscal/component-definition.json
   ```
6. Run the drift tests:
   ```bash
   swift test --filter Compliance
   ```
7. Commit the OSCAL artifact in the same PR as the `SECURITY.md` change that
   prompted it. CI will fail if you split them.

## Workflows for the POA&M and Assessment Results artifacts (STORY-037)

### When to update `plan-of-action-and-milestones.json`

Edit the POA&M whenever any of the following lands:

1. A new accepted-risk statement is added to `docs/SECURITY.md` §4 (must also
   add a poam-item with `props[name=security-md-section]` matching).
2. An existing §4 accepted-risk statement is removed (must flip the
   matching poam-item's status away from `open`/`risk-accepted` and add
   closure evidence to `remarks`).
3. A milestone in an open item completes or its target date changes.
4. The named `poam-owner` role transfers.

Bump `metadata.last-modified` and `metadata.version` on consumer-visible
changes. New item UUIDs go in `poam-id-allocations.md`.

### When to update `assessment-results.json` (mostly automatic)

You normally don't edit this file by hand — CI does it via
`swift run oscal-emit`:

```bash
swift run oscal-emit path/to/audit-records.jsonl oscal/assessment-results.json
```

Each invocation appends new observations (deduped by UUID, idempotent on
re-run). The nightly integration job is the canonical producer; manual
runs are useful for verifying the pipeline on a fixture stream.

### Drift detection

`swift run oscal-drift check` runs both checks bi-directionally on every PR:

- `check-controls` — `docs/SECURITY.md` §7/§8 ↔ `component-definition.json`
  (STORY-022 coverage).
- `check-section4-poam` — `docs/SECURITY.md` §4 ↔ `plan-of-action-and-milestones.json`
  (STORY-037 coverage).

CI fails if any check reports drift, with a `*_drift` token in the
error message naming exactly which artifact lost sync.

## Out of scope (future work)

- **System Security Plan** (`system-security-plan.json`) — different stakeholder
  (deployer), different document; not committed here.
- **Assessment Plan** — produced by the consuming assessor, not by the
  system owner. The Assessment Results artifact's `import-ap` references a
  placeholder href until an assessor authors a real AP.
