# AuditRecord → OSCAL Observation Mapping

This document is the human-readable companion to `Sources/OSCALComplianceSupport/EventTypeMapping.swift`. It tells an assessor reading `oscal/assessment-results.json` how to interpret each observation in terms of the source `AuditRecord` event and the NIST SP 800-53 controls the observation is evidence for.

The Swift map is the authoritative source; this document is regenerated by hand when new event types are added. The `EventTypeMappingTests` suite verifies that every value of `AuditEventType` has a row in the Swift map; the OSCAL artifact structural tests verify each row's `controls` field references control IDs that actually exist in `oscal/component-definition.json`.

## Event-type mapping

| AuditRecord event type (+ disposition) | OSCAL Observation `title` | `methods` | Related controls | `elevated` |
|----------------------------------------|---------------------------|-----------|------------------|------------|
| `applescript_execute` + `allowed`             | `applescript_executed`              | `EXAMINE` | AU-2, AU-3, CM-7 | — |
| `applescript_execute` + `rejected_security`   | `applescript_rejected`              | `EXAMINE` | SI-10, CM-7 | — |
| `applescript_execute` + `rejected_permission` | `applescript_rejected`              | `EXAMINE` | SI-10, CM-7 | — |
| `applescript_execute` + `not_applicable` (defensive) | `applescript_rejected`       | `EXAMINE` | SI-10, CM-7 | — |
| `menu_click`                                 | `click_menu_item_invoked`           | `EXAMINE` | AU-2, AU-3 | — |
| `menu_alternatives_lookup`                   | `menu_alternatives_lookup`          | `EXAMINE` | AU-2, AU-3 | — |
| `chain_verification_failure`                 | `run_applescript_audit_chain_break` | `TEST`    | AU-9 | ✓ |
| `administrative_force_rotate_unacked`        | `administrative_force_rotate_unacked` | `EXAMINE` | AU-9, AU-11 | — |

`elevated = ✓` means the observation additionally populates `related-risks` referencing the chain-break risk UUID. The corresponding POA&M item (`f17c8b39-6f53-4bd1-93d6-c44e1aac9b91`) is the assessor's entry-point for follow-up.

## Field-level mapping

Each `AuditRecord` field maps to OSCAL Observation fields as follows:

| AuditRecord field                  | OSCAL Observation field                                                       |
|------------------------------------|-------------------------------------------------------------------------------|
| `record_id`                        | `uuid` (deterministically derived); `relevant-evidence[0].href`              |
| `timestamp_iso8601`                | `collected`                                                                   |
| `event_type` + `filter_disposition`| `title`, `methods`, `links[rel=control]` (via EventTypeMapping)              |
| `target_apps_extracted[i]`         | `subjects[type=component].title`                                              |
| `host_identifier`                  | `subjects[type=party].title`                                                  |
| `script_sha256`                    | `subjects[type=evidence].title` (when present and non-zero)                  |
| `execution_outcome`                | `props[name=execution-outcome].value`                                         |
| `filter_disposition`               | `props[name=filter-disposition].value`                                        |
| `record_hash` / `prev_hash`        | `props[name=audit-record-hash]` / `props[name=audit-prev-hash]`              |
| `audit_schema_version`             | `props[name=audit-schema-version].value`                                      |
| `duration_ms`                      | `props[name=duration-ms].value`                                               |
| `rejection_reason` (optional)      | `props[name=rejection-reason].value`                                          |
| `denied_app` (optional)            | `props[name=denied-app].value`                                                |
| `script_error_code` (optional)     | `props[name=script-error-code].value`                                         |

`relevant-evidence[0].href` is an `audit-records://` URI of the form `audit-records://<iso8601>/<record-id>`. It is a logical handle, not a fetchable URL — assessors join it back to the on-disk log under `~/Library/Logs/com.mcp.macos-control/audit/` (see `docs/AUDIT-LOG-OPERATIONS.md`).

The "tool" subject (`subjects[type=tool].title`) is inferred from the event type because `AuditRecord` does not carry the MCP tool name as a first-class field today:

| `event_type`                          | Inferred tool name        |
|---------------------------------------|---------------------------|
| `applescript_execute`                 | `run_applescript`         |
| `menu_click`                          | `click_menu_item`         |
| `menu_alternatives_lookup`            | `click_menu_item`         |
| `chain_verification_failure`          | `verify_audit_chain`      |
| `administrative_force_rotate_unacked` | `force_rotate_unacked`    |

When `AuditRecord` learns to carry the tool name as a field, the inference goes away and the field maps directly.

## Why deterministic Observation UUIDs

`OscalObservationEmitter` derives each Observation's UUID from the AuditRecord's `record_id` using a SHA-256 namespace digest with the v4 version/variant bits set. Two consequences:

1. **Re-runs are idempotent.** `oscal-emit` invoked twice on the same input stream produces the same Observation UUIDs and the second run appends zero new observations to `assessment-results.json` (the appender dedupes on UUID).
2. **Tampering is detectable.** A malicious actor who appends a fake Observation to the AR cannot also forge the deterministic UUID for an AuditRecord that doesn't exist in the source chain; chasing the UUID back through `OscalObservationEmitter` is the audit handle.
